# YSKAR Wallet: the Android app

This document is the developer and maintainer reference for the Android app "YSKAR Wallet" and
for the parts of the web UI that exist because of the app. It covers the repository layout, the
signing key, releases, native mining, biometrics, push notifications, the widget, a device test
checklist and troubleshooting.

## What the app is

The app is a native shell built with Capacitor around the same web UI that runs as the Telegram
Mini App. The shell does not contain the UI. It loads it from `https://yskar.vercel.app`
(`server.url` in `capacitor.config.ts`), so every change to the web app reaches the app
immediately. A new APK is needed only when the shell itself changes: permissions, plugins, the
mining service, the widget, the icon. Without a network connection Android shows
`native/www/offline.html`.

| Identifier | Value | Source |
|---|---|---|
| Application ID | `net.yskar.wallet` | `capacitor.config.ts`, `android/app/build.gradle` |
| App name | YSKAR Wallet | `capacitor.config.ts` |
| Minimum Android version | API 24 (`minSdkVersion`) | `android/variables.gradle` |
| Compile and target SDK | API 36 | `android/variables.gradle` |
| Orientation | portrait | `AndroidManifest.xml` |

What the app can do that the Mini App cannot:

| Feature | Description |
|---|---|
| Background mining | A foreground service mines with the screen off and shows a notification with a stop button. |
| Biometrics | Unlock and send with fingerprint or face. The PIN remains the fallback. |
| Push notifications | Incoming payment, confirmation, block found, news. They arrive when the app is closed. |
| Widget | A home screen widget with a mining overview. |
| Updates | A notice in the app as soon as a newer release is on GitHub, with download and installer. |

The web UI finds out where it runs through `plattform()` in `src/lib/native/plattform.ts`. It
returns `nativ` (the Android app), `telegram` (the Mini App) or `browser`. The functions in
`src/lib/native/` that talk to the shell check this first and do nothing outside the app.

## Signing key

Android accepts an update only if it is signed with the same key as the installed version. The
keystore must never be committed to the repository and must not be lost. If it is lost, no
existing installation can be updated and every user has to install the app again.

```bash
keytool -genkeypair -v -keystore yskar.jks -alias yskar \
  -keyalg RSA -keysize 4096 -validity 10000 \
  -dname "CN=YSKAR Wallet, O=YSKAR"
base64 -w0 yskar.jks > yskar.jks.b64
```

Run these commands in a directory outside the repository. `.gitignore` does not exclude `*.jks`
or `*.b64` files, so a keystore created inside the working tree could be committed by mistake.

The release workflow reads these repository secrets (GitHub: Settings, Secrets and variables,
Actions):

| Secret | Content |
|---|---|
| `YSKAR_KEYSTORE_BASE64` | The keystore file, Base64-encoded without line breaks |
| `YSKAR_KEYSTORE_PASSWORD` | Password of the keystore |
| `YSKAR_KEY_ALIAS` | Alias of the key inside the keystore |
| `YSKAR_KEY_PASSWORD` | Password of the key |
| `GOOGLE_SERVICES_JSON` | Content of `google-services.json` from Firebase (see Push notifications) |

Keep the keystore file and its passwords in a password manager or an encrypted backup.

`android/app/build.gradle` takes the keystore path from the environment variable
`YSKAR_KEYSTORE_FILE` and the passwords and alias from the variables named above. Without a
keystore the release signing configuration is not created.

## Publishing a release

```bash
git tag app-v1.2.3
git push origin app-v1.2.3
```

A tag that matches `app-v*` starts the workflow "Android-App bauen und veröffentlichen"
(`.github/workflows/android-release.yml`, job `apk`). It installs Node.js 22, Java 21 (Temurin)
and the Android packages `platforms;android-36` and `build-tools;36.0.0`, runs `npm ci` and
`npx cap sync android`, and builds with Gradle.

| Property | Rule |
|---|---|
| `versionName` | The tag without the prefix `app-v`. Without a tag: `0.0.<run number>-test`. |
| `versionCode` | `1000 + GITHUB_RUN_NUMBER`. It rises with every run, so nobody has to maintain it. |
| Build type | `assembleRelease` when the keystore secret is set, otherwise `assembleDebug`. |
| File name | `yskar-wallet-<versionName>.apk`, or `yskar-wallet-<versionName>-debug.apk` for a debug build |
| Checksum | `<file name>.sha256`, written with `sha256sum` |
| Artifact | Every run uploads the APK and the checksum as a workflow artifact. |
| Release | Only for a tag and a signed build: release "YSKAR Wallet <versionName>" with APK and checksum. |

A run started by hand (`workflow_dispatch`) therefore produces a test artifact and no release.
Its input `app_url` builds an APK that loads the UI from another address, for example a preview
deployment. Leave it empty for production.

A debug build is signed with Gradle's debug key. It can be installed for testing, but it cannot
replace an installed release build, because the signatures differ.

The app looks for updates itself: it reads the list of GitHub releases, keeps the ones whose tag
matches `app-vX.Y.Z` and that are neither drafts nor pre-releases, and compares the newest with
its own version (`src/lib/native/update.ts`). Other tags in the repository are ignored.

## Building locally

```bash
npm ci
npx cap sync android
cd android && ./gradlew assembleDebug
```

You need the Android SDK and Java 21. The release workflow installs the platform `android-36`
and the build tools `36.0.0` for its build. Without `-PversionName` and `-PversionCode` the build uses
`0.0.0-dev` and `1`.

The local build also loads the production UI. To load another server, set `YSKAR_APP_URL`
before `npx cap sync android`. The value must start with `http://` or `https://`; an empty value
counts as not set. `capacitor.config.ts` sets `cleartext: false` and the manifest sets
`android:usesCleartextTraffic="false"`, so a plain `http://` development server is blocked
unless you change these settings for your local build. Do not commit such a change.

If `android/app/google-services.json` is missing, the build still works; the Google services
plugin is not applied and push notifications do not work in that build.

`npm run app:assets` regenerates the icon and splash images from the files in `assets/`.

## Mining in the app

There are two mining paths. `useMiningApp` (`src/hooks/useMiningApp.ts`) chooses once, when the
UI starts, and the rest of the UI does not notice the difference.

| Where | Path | Who computes |
|---|---|---|
| Android app, APK 1.0.9 and later | `useMiningNativ` | The foreground service, in Java threads (`NativMiner.java`) |
| Android app, APK up to 1.0.8 | `useMining` | Web Workers in the WebView; the service only keeps process and CPU awake |
| Telegram Mini App, browser | `useMining` | Web Workers; mining stops when the page is hidden |

The UI recognizes an APK with the native miner by the user-agent suffix `YSKAR-NativMining/1`,
which `capacitor.config.ts` appends (`android.appendUserAgent`). `nativMiningVerfuegbar()` in
`src/lib/native/nativMining.ts` checks for it.

### Native mining (APK 1.0.9 and later)

The reason for the native path is recorded in the code: the WebView suspends its workers shortly
after the app goes to the background, even while the foreground service is running. Threads of
the service are not affected.

`NativMiner` speaks the same HTTP interface as the web miner and the CLI miner:

| Request | Purpose |
|---|---|
| `POST {basis}/api/v2/session` `{address, platform, mode}` | Open a session |
| `GET {basis}/api/v2/job?session=` | Fetch a job with the header fields and the share target |
| `POST {basis}/api/v2/share` `{sessionId, jobId, nonce}` | Submit a nonce |
| `POST {basis}/api/v2/session/stop` `{sessionId}` | Close the session |

`basis` is the node the UI passes in: the chosen pool in pool mode, otherwise the address from
`NEXT_PUBLIC_MINING_BASE`, otherwise the origin of the web app. A share is a hash that meets
the target the node set for this session; it proves work without being a block. The node
recomputes every share; the miner only sends nonces.

How it works:

- **Threads.** One control thread (session, a new job every 40 seconds or at once when needed),
  one sender thread (submits found nonces), and one computing thread per configured thread
  (1 to 16). Each computing thread searches its own section of the nonce space.
- **Hashing.** `Rechenweg` offers three implementations with the same result: `schleife` (plain
  Java with midstate), `kern` (unrolled Java with midstate, `Sha256dKern`) and `digest` (the
  system's `MessageDigest`). At start the miner measures each one briefly on the device and uses
  the fastest. The measured values go into the log.
- **Power control.** `duty` is a percentage from 1 to 100. After each batch the thread sleeps in
  proportion, so a lower value means fewer hashes computed.
- **Thread priority.** The computing threads run slightly below normal priority (nice value 5).
- **Stale jobs.** A share rejected with `job_expired`, `stale_job`, `job_foreign`, `job_unknown`
  or `session_inactive` makes the miner fetch a new job at once. A session the node has dropped
  is reopened.
- **Errors that end mining.** A session the node refuses (invalid address, no pool on this node,
  pool full) and a pool session that the node answers as solo stop the miner. The service then
  sends the `stop` event to the UI and ends; the UI reads the reason from `nativStatus`.
- **Identification.** The miner sends the user agent `YSKAR-Wallet-Nativ/1`. The node answers
  `pool_full` to this client with HTTP 200 instead of 409
  (`src/lib/node/fullnode/MiningServer.ts`), because this miner treats every status from 400 as
  a network error and would retry.

The plugin `MiningService` (`MiningServicePlugin.java`) exposes this to the UI:

| Method or event | Purpose |
|---|---|
| `faehigkeiten()` | Returns `{ nativMining: true, version: 1 }` |
| `nativStart({ basis, address, mode, platform, threads, duty, vorlage })` | Start service and miner. `vorlage` is the notification text with the placeholder `{rate}`, in the language of the app. |
| `nativDuty({ duty })` | Change the power setting while mining |
| `nativStatus()` | State of the miner as JSON, plus the last 80 log lines |
| `stop()` | End miner and service |
| `ping()` | Diagnostics: is the service running, heartbeat times, time of the last message |
| event `stop` | The user tapped "Stop mining" in the notification or in the widget, or the miner ended with an error |

While mining, `useMiningNativ` reads `nativStatus` once per second. If the WebView is reloaded
or the app is opened again while the service is mining, the UI takes over the running miner.

### WebView mining (APK up to 1.0.8, Telegram, browser)

`useMining` starts Web Workers (`src/workers/miner.worker.ts`) that run the WASM engine. In the
Android app it additionally calls `start({ text })` on the plugin, which starts the service
without a miner, and `update({ text })` every four seconds for the hashrate in the notification.
`MainActivity` sets the renderer priority of the WebView to "important" also when it is not
visible, so that Android does not freeze the renderer process together with the workers.

Outside the Android app, `useMining` stops mining when the page becomes hidden, and closes the
session at the node.

### The foreground service

`MiningService` is a foreground service of type `specialUse`; the manifest states the reason
(proof-of-work mining, started by the user, stoppable through the notification). It holds a
`PARTIAL_WAKE_LOCK`: the CPU stays on and the screen may turn off. The notification is silent,
shows the hashrate and the power setting, and has a stop action. From Android 13 the
notification needs the permission `POST_NOTIFICATIONS`; the plugin asks for it at the first
start and starts the service even if the user declines.

Limits: the battery optimization of some manufacturers can still end the service. The only
remedy is to exempt the app from battery optimization in the system settings. Mining in the
background uses battery and produces heat. That is the computation, not a bug.

## Biometrics

Biometrics does not change how the wallet is encrypted. The 12 words stay encrypted with the PIN
(see [SECURITY.md](SECURITY.md)). When you turn biometrics on, the app stores your PIN through
the plugin `@aparajita/capacitor-secure-storage`, which encrypts it with a key from the Android
Keystore. For unlocking and sending, the app first asks for the system's biometric confirmation
and reads the PIN afterwards (`src/lib/native/biometrie.ts`).

- The device PIN or pattern is not accepted in place of the sensor (`allowDeviceCredential:
  false`). The fallback is the app's own PIN.
- Turning biometrics on requires the sensor once, so that nobody can enable it unnoticed.
- This protects against someone who holds your unlocked phone. It does not protect against a
  device with root access; there the stored PIN could be read without the sensor. Root access
  weakens the PIN itself in the same way, because the vault can be copied and the PIN tried
  offline. If you do not want the PIN stored on the device, leave biometrics off.
- If the stored PIN no longer matches the wallet (after restoring with a new PIN), biometrics
  turns itself off at the next attempt.
- Outside the Android app every function answers as if there were no sensor.

## Push notifications

Three parts are needed.

**1. Firebase project.** Only Cloud Messaging is used. Create a project, add an Android app
with the package name `net.yskar.wallet`, download `google-services.json` and store its content
as the secret `GOOGLE_SERVICES_JSON`. Then generate a private key for a service account
(Project settings, Service accounts) and put the JSON file on the machine that runs the watcher,
readable only by the service user.

**2. Database.** Apply the migration `supabase/migrations/00018_push_und_news.sql`. It creates
`chain2.push_geraete` (devices), `chain2.push_versendet` (what was already sent),
`chain2.push_stand` (the watcher's position) and `chain2.news`.

**3. Watcher.** `scripts/push-watcher.ts` runs as a service on a machine that can reach a full
node, most simply next to the node itself:

```ini
# /etc/systemd/system/yskar-push.service
[Unit]
Description=YSKAR Push-Watcher
After=network-online.target

[Service]
WorkingDirectory=/opt/yskar
Environment=NEXT_PUBLIC_SUPABASE_URL=https://….supabase.co
Environment=SUPABASE_SERVICE_ROLE_KEY=…
Environment=YSKAR_FULLNODE_URL=https://yskar-main.dynv6.net
Environment=FCM_SERVICE_ACCOUNT_FILE=/etc/yskar/fcm.json
ExecStart=/usr/bin/node --experimental-strip-types scripts/push-watcher.ts
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

| Variable | Meaning |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Access to the device list, the watcher's position and the news |
| `YSKAR_FULLNODE_URL` | The node the watcher reads blocks and pending transfers from |
| `FCM_SERVICE_ACCOUNT_FILE` | Path to the JSON file of the Firebase service account |
| `PUSH_TAKT_MS` | Polling interval in milliseconds, default 8000 |

The service role key bypasses row level security, and a unit file under `/etc/systemd/system`
is readable by every user of the machine. To keep the key out of the unit, put the variables
into a file that only root can read (mode 600) and name that file with `EnvironmentFile=`
in place of the `Environment=` lines.

What the watcher does in every pass:

1. Load the device list.
2. Read the blocks since its last position (`/api/v2/summary`, `/api/v2/blocks/<height>`). A
   transfer to a registered address gives the event `ok` ("received"); a coinbase output to a
   registered address gives the event `block` ("block found", or "pool share" when the coinbase
   has several recipients). After a long pause it starts at most 50 blocks below the tip.
3. For every registered address read the pending incoming transfers
   (`/api/v2/account/<address>`): event `in` ("on the way").
4. Send news entries that have `push = true` and were not sent yet, to all devices.

Every event is sent once per device; `push_versendet` remembers the keys `in:<txid>`,
`ok:<txid>`, `block:<height>` and `news:<id>`. Entries older than 30 days are deleted. Tokens
that Firebase reports as invalid are removed from `push_geraete`. Outgoing payments are not
reported.

On the device (`src/lib/native/push.ts`): push is opt-in in the settings. When you turn it on,
the app asks for the notification permission, creates the Android channels `wallet` and `news`,
obtains a token and registers it with the wallet address through `POST /api/v2/push/register`.
Turning it off deletes the token on the server (`POST /api/v2/push/unregister`). At every start
the app refreshes the registration if push is on.

**Privacy.** `push_geraete` links an address to a device, which is more than the chain knows.
This is why push is opt-in and can be turned off at any time. The register route does not ask
for proof that the caller owns the address: whoever registers a foreign address learns only what
is public in the chain anyway.

## News

News entries are stored in `chain2.news`. Create one through the API with the token from the
environment variable `YSKAR_ADMIN_TOKEN` of the Vercel deployment:

```bash
curl -X POST https://yskar.vercel.app/api/v2/news \
  -H "authorization: Bearer $YSKAR_ADMIN_TOKEN" \
  -H "content-type: application/json" \
  -d '{"titel":"…","text":"…","titel_en":"…","text_en":"…","link":"https://…","push":true}'
```

| Field | Meaning |
|---|---|
| `titel`, `text` | German title (up to 120 characters) and text (up to 2,000 characters). Required. |
| `titel_en`, `text_en` | English version (migration `00019_news_englisch.sql`). Optional. |
| `link` | Optional `http://` or `https://` address |
| `push` | `true`: the watcher sends the entry to all devices in its next pass |
| `datum` | Optional date in the form `YYYY-MM-DD` |

`GET /api/v2/news?sprache=<code>` returns the newest 20 entries. German gets the German text.
Every other language gets the English version where it exists and the German text otherwise;
the table holds no other translations. The same rule applies to the push text.

If `YSKAR_ADMIN_TOKEN` is not set, the route answers 401; entries can then be created directly
in Supabase. If the table is empty or cannot be reached, the route returns the built-in entries
from the source code instead (`NEUIGKEITEN_DE` or `NEUIGKEITEN_EN` in `src/content/entdecken.ts`).

## Widget

The home screen widget is a mining overview. The widget exists since APK 1.0.5; the mining
overview and the choice between a light and a dark widget came with APK 1.1.0. It does not show
the wallet balance.

- **Mining is running:** "earned this session", a stop button, and below them hashrate, runtime
  and accepted shares.
- **Mining is stopped:** the state of the network: block height, network hashrate, block reward.
- **No wallet set up:** a short notice.

A tap on the widget opens the app. The arrow fetches the network state at once. The stop button
ends mining the same way as "Stop mining" in the notification.

`android/app/src/main/res/xml/widget_info.xml` defines a target size of 4 by 2 cells. The widget
can be resized in both directions. There is one layout per theme, `widget.xml` and
`widget_dunkel.xml`, with the same structure and the same view IDs; change both together. The
user chooses the theme under Settings, App, Widget (`WidgetPlugin.thema`).

Where the values come from (`WidgetDaten.java`, `YskarWidget.java`):

- **Mining values.** `MiningService` writes hashrate, accepted shares and share difficulty into
  the widget's storage every four seconds and remembers when the session began.
- **Earned this session.** `GET /api/v2/account/<address>/verlauf?richtung=ein&limit=200&von=<start>`
  from the start of the session; block rewards and pool shares are counted, ordinary transfers
  are not. The service asks after a block change, which the miner sees because the height of
  its job changes, and otherwise every ten minutes. The chain does not know which device did
  the work: if the same address mines elsewhere at the same time, that counts too.
- **Network state.** `GET /api/v2/summary`: every 30 minutes through Android's `onUpdate`, when
  the arrow is tapped, after mining stops, and at most every five minutes while the app is open.
- **Address.** The web UI reports it through the plugin `Widget` (`src/lib/native/widget.ts`).

The widget reads from `https://yskar.vercel.app`; the address is fixed in `WidgetDaten.BASIS`
and does not follow `YSKAR_APP_URL`.

If not everything fits into the height (small launcher grids, large system font),
`YskarWidget.einpassen` first drops the line below the large number, then the labels of the
three fields, then the fields.

## Update from inside the app

At start the app checks for a newer release (`UpdateBanner`). The banner "Update x.y.z
available" downloads the APK through Android's `DownloadManager` and opens the installer; the
user only confirms. The plugin `AppUpdate` (`AppUpdatePlugin.java`) has three methods:

| Method | Purpose |
|---|---|
| `laden({ url, version })` | Start the download; returns `laedt` (downloading) or `erlaubnis` (permission needed). Only `https://` addresses are accepted. |
| `stand()` | Progress: `laedt`, `fertig` (done), `fehler` (failed) or `keins` (none), and a percentage |
| `installieren()` | Open the installer again for the APK downloaded last |

The first time, Android requires the permission "Install apps from this source". `laden` then
opens the settings page and the app asks the user to tap again afterwards. If the plugin is
missing (an older shell) or the download fails, the app opens the download in the browser. A
fully automatic update without confirmation is not possible outside the Play Store.

Android installs the downloaded APK over the existing app only if it carries the same
signature. Wallet and settings are kept.

## Notice about the app in Telegram and in the browser

Whoever uses YSKAR on an Android device in Telegram or in a browser sees a notice about the
Android app once (`src/components/AppLaden.tsx`): version and size of the newest APK from GitHub
Releases, three installation steps including the permission "Install unknown apps" for Telegram
or Chrome, and the reason for that permission. "Later" postpones the notice by seven days,
"Don't show again" hides it for good (`localStorage` key `yskar.apk.hinweis`). The same notice
is an entry in the settings. Nothing appears in the app itself or on devices that are not
Android.

## Languages

The UI exists in ten languages: English, German, Spanish, Portuguese (Brazil), French, Italian,
Polish, Russian, Turkish and Chinese (`SPRACHEN` in `src/i18n/index.tsx`).

- All texts are in `src/i18n/<code>.ts` with identical keys. `de.ts` defines the type; a key
  that is missing in another file is a build error.
- Articles, FAQ and the built-in news are in `src/content/entdecken.<code>.ts`.
- Default: the remembered choice (`localStorage` key `yskar.sprache`), otherwise Telegram's
  `language_code`, otherwise the system language, otherwise English. The language can be chosen
  on the first screen and in the settings.
- Push texts follow the language the device reported (`push_geraete.sprache`), with English as
  the fallback (`src/lib/push/ereignisse.ts`).
- The widget and, in the notification of the mining service, the title and the stop button
  follow the Android system language (`android/app/src/main/res/values` for English and
  `values-<code>` for the other nine). The text line of the notification comes from the web UI
  in the language of the app.
- The offline page `native/www/offline.html` has texts in six languages: English, German,
  Russian, Spanish, Turkish and Portuguese.

To add a language: create `src/i18n/<code>.ts` and `src/content/entdecken.<code>.ts`, register
both in `src/i18n/index.tsx` and `src/content/entdecken.ts`, and add the texts in
`src/lib/push/ereignisse.ts`, `native/www/offline.html` and
`android/app/src/main/res/values-<code>/strings.xml`.

## Wallet screens

The wallet tab shows a balance card, the actions Send, Scan and Receive, a tile "mining
earnings", pending payments and the history. This part of the UI is the same in the app and in
the Mini App.

- **History.** Grouped by day. The mining earnings of one day stand in one line with count and
  sum, and can be expanded down to the single block (`src/lib/wallet/verlaufGruppen.ts`). A page
  has 40 entries and does not end at midnight, so the oldest loaded day is usually cut off. The
  list therefore fetches the rest of exactly that day (parameter `von=` of the history route)
  before it shows a sum. With an active search, entries are not grouped.
- **Mining earnings and "today".** `GET /api/v2/account/<address>/einnahmen?tage=30&tz=<zone>`
  returns, per calendar day in the device's time zone, the mining earnings (`summe`, `bloecke`)
  and the received transfers (`eingaenge`). The data comes from the database functions
  `chain2.einnahmen_tage` and `chain2.eingaenge_tage` (migration `00024_einnahmen_tage.sql`).
  `tage` may be 1 to 90; without `tz` the days are counted in UTC.
- **Send** in four steps: recipient, amount (own number pad, `src/lib/wallet/ziffern.ts`),
  review, sent. The review step shows the address in full, in groups of four, and says whether
  you have sent to it before; otherwise it says "New address". The transfer is built and signed
  on the device.
- **Contacts.** Names for addresses, stored only on the device (`localStorage`,
  `src/lib/wallet/kontakte.ts`). No server knows them. They do not move along when the wallet
  is restored elsewhere, and they are deleted when the wallet is removed from the device.
- **Request an amount.** The QR code then carries `yskar:<address>?amount=25.5&memo=…`
  (`src/lib/wallet/qr.ts`). Older versions of the app read the address from it and ignore the
  rest. Amount and memo are a suggestion; nothing is sent before the review step.
- **Hide balance.** The eye next to the balance replaces all amounts in the wallet and on the
  home tab with dots until you tap it again. This is no protection against someone who holds
  the phone; the app lock is there for that.
- **Amounts.** Two to four decimal places in the notation of the chosen language, truncated and
  never rounded (`src/lib/wallet/betrag.ts`).

## Pool selection

In the mining tab you choose the pool from a list instead of typing an address
(`src/hooks/usePoolAuswahl.ts`).

- **List.** `GET /api/v2/pools`. The server asks every pool in `src/lib/pool/verzeichnis.ts` for
  its state (`GET <pool>/api/v2/pool`) and counts the blocks each pool found from the chain
  (migration `00025_finder_namen.sql`). The answer is at most about 20 seconds old. The app
  reloads it every 20 seconds while the mining tab is visible. States: `offen` (open), `voll`
  (full), `unbekannt` (reachable, but an older node that reports no seats), `keinPool` (the
  address answers, but runs no pool), `aus` (does not answer). Where the list says full or not
  answering, the app asks the pool itself once more, and the pool's answer counts.
- **Suggestion.** Without a remembered choice, the first open pool of the list is preselected.
  The app remembers what you choose or start with (`localStorage` keys `yskar.pool` and
  `yskar.mining.modus`).
- **Before the start** the app asks the pool directly, with your own address, and waits up to
  four seconds. Full and your address has no seat: no start, and a notice in the language of
  the app. If the pool does not answer or does not know the question, mining starts as before;
  the actual limit is enforced by the pool node.
- **Full, but already in.** An address that already holds a seat (a second device) can still
  choose the pool. To learn this, the app sends your address to the chosen pool and, while the
  list is open, to the full ones. No other pool receives the address in the background.
- **If `/api/v2/pools` fails,** the app asks the pools of the last list itself. The remembered
  pool stays usable.
- **Custom address.** For pools that are not in the list.
- `useMining`, `useMiningNativ` and the miners are not affected by any of this. Mining receives
  only the address of the pool node, as before.

How pools work, seats and the list itself are described in [POOL.md](POOL.md).

## UI building blocks

`src/components/ui/Bausteine.tsx` contains the components of the current design: `Zahl` (large

## Light and dark theme

Settings, Appearance: System, Light or Dark, remembered under the `localStorage` key
`yskar.thema`, the same key the explorer reads. "System" follows the device; inside Telegram it
follows the color scheme of the Telegram client (`src/lib/thema.ts`).

- The colors are tokens in `src/app/globals.css` under `:root[data-thema="dunkel"]`. A start
  script (`THEMA_STARTSKRIPT`) sets the attribute before the first paint.
- The web splash uses `public/marke/splash-dunkel.jpg` in the dark theme.
- The native Android splash uses the `drawable-*-night` variants generated from
  `assets/splash-dark.png`. It follows the system setting, not the choice in the app, because
  it runs before the UI is loaded.
- The plugin `Oberflaeche` colors the icons of the system bars (`leisten({ dunkel })`); it is
  missing in shells before APK 1.0.8, where the icons stay dark. Inside Telegram,
  `telegramFarben(dunkel)` sets the frame colors.

## Device test checklist

Use this list after a change to the shell, on a real device. A test build comes from a manual
run of the workflow (see Publishing a release): download the artifact, which GitHub delivers as
a ZIP file, and install the APK from it. Android asks once for the permission to install from
that source. Uninstall a build with a different signature first.

- [ ] The splash image appears, then the welcome screen, not the screen "YSKAR runs in
      Telegram".
- [ ] Create a wallet, or restore one with 12 words; set a PIN.
- [ ] The home tab shows balance and chain; the block number is not a dash.
- [ ] Settings, Security, "Fingerprint / face", "Turn on biometrics": enter the PIN, the system
      dialog appears, then the entry reads "Active for unlocking and sending."
- [ ] Close the app completely and open it again: the sensor dialog appears at once and
      unlocking works without the PIN.
- [ ] Wallet, Send: "Send with fingerprint / face" replaces the PIN field. Test with a small
      amount to a second wallet.
- [ ] Send, Scan: the camera permission is requested, and the QR code from another device's
      Receive screen is recognized and filled in.
- [ ] Start mining, press the home button and lock the screen. The notification "YSKAR is
      computing" shows "Mining running" with the hashrate. Unlock after two minutes: the share
      chart has new bars. "Stop mining" in the notification ends it.
- [ ] Add the widget to the home screen. While mining it shows the session earnings and the
      stop button; when stopped it shows block, network and reward.
- [ ] Settings, App shows the version of the build.
- [ ] With a build that contains the Firebase configuration, and with the watcher running: turn
      on notifications in the settings and receive a transfer from a second wallet. The
      notifications "on the way" and "received" arrive.
- [ ] With a release build and a newer release on GitHub: the banner "Update x.y.z available"
      appears at start; "Download" loads the APK and opens the installer; wallet and settings
      are kept.

A build without the Firebase secret has no push notifications. A test build has the version
name `0.0.<run number>-test`, which is older than every release, so the update banner appears in
it whenever a release exists.

Settings, App, Diagnostics, "Run" shows what the native bridge reports: platform, registered
plugins, app version, biometry check, the service's heartbeat, the last errors of the UI, the
mining log and, with native mining, the state and log of the native miner
(`src/lib/native/diagnose.ts`).

## Troubleshooting

| Symptom | Cause | What to do |
|---|---|---|
| The Actions run fails | Build error | Open the run, job `apk`; the failed step shows the log. |
| "App not installed" | A build with a different signature is installed | Uninstall the existing YSKAR Wallet first. |
| The app shows "No connection" | No network, or the web app cannot be reached | Check the network and tap "Try again". |
| White screen for more than ten seconds | The web app does not load | Open `https://yskar.vercel.app` in a browser to see whether it loads there. |
| The biometrics entry says "No sensor reported." | The device has no fingerprint or face sensor | Expected. The PIN remains. |
| The biometrics entry says "Not set up in the Android system." | No fingerprint or face is enrolled | Enroll one in the Android settings, then "Check again". |
| Mining stops with the screen locked | Battery optimization of the manufacturer | Settings, Apps, YSKAR Wallet, Battery: set to unrestricted. |
| No camera image when scanning | The permission was denied | Settings, Apps, YSKAR Wallet, Permissions, Camera. |
| No push notifications | Build without `google-services.json`, permission denied, or the watcher is not running | Check the build, the Android permission and the watcher's log. |
| The update banner asks to tap again | Android needs "Install apps from this source" | Allow it on the settings page that opened, go back and tap again. |

## Not available

- **iOS.** The repository contains no iOS project.
- **Google Play.** The app is distributed as an APK through GitHub Releases, not through the
